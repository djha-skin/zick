Short how-tos for common things you can do with zick. Each recipe assumes you are inside a zick project (one with a .zick-db directory at or above your current directory); run zick init first if you do not have one.

Pinning a Version

Install a specific version of a package from its archive URL:

zick add -k mylib -V 1.2.0 -l https://example.com/mylib-1.2.0.zip

The version is recorded verbatim in the store, and zick verify checks the installed files against the recorded checksums — so the pinned version stays pinned until you upgrade it.

Installing a Package with a Dependency

Declare that one package depends on another with -u. The dependee must already be installed:

zick add -k mylib -V 1.2.0 -l https://example.com/mylib-1.2.0.zip
zick add -k myapp -V 0.1.0 -l https://example.com/myapp.zip -u mylib

zick dependers -k mylib now reports myapp, and zick remove -k mylib refuses to remove it unless you pass -c to cascade.

Upgrading a Package

Re-add the package with the new version. zick removes the old files, puts changed configuration files aside, and keeps unchanged ones:

zick add -k mylib -V 1.3.0 -l https://example.com/mylib-1.3.0.zip

If the new version compares equal to the installed one, zick treats it as an in-place replacement and errors unless you pass -i/--enable-allow-inplace. Re-adding at a lower version is a downgrade and errors unless you pass -g/--enable-allow-downgrades.

Verifying an Install After a Restore

After a git clean, a restore from backup, or a fresh checkout, check that the files on disk still match the store:

zick verify -k mylib

Exits 0 when everything matches, 3 when the package is not installed, and 4 when verification finds problems — printing the failing files grouped by failure kind. Run zick verify for every installed package, or re-add each package to repair the tree.

Recording Metadata Without Downloading

Record a package from its options alone, without touching the network or the project tree:

zick add -k mylib -V 1.2.0 -l https://example.com/mylib-1.2.0.zip -W

-W — download disabled — is useful for recording metadata-only records, or for tests that exercise the store without network access. A -W record has no files; to install them later, re-add the package with downloading enabled — passing -i/--enable-allow-inplace, since re-adding at the already- recorded version counts as an in-place replacement.

Declaring Configuration Files

Tell zick which files a package installs are configuration — files a local edit might change, which upgrades should preserve rather than clobber. Pass JSON metadata on the command line:

zick add -k myapp -V 0.1.0 -l https://example.com/myapp.zip \
    -m '{"zick": {"config-files": ["etc/myapp.conf"]}}'

zick records such files as config-file rather than normal-file: verification only checks that they exist, removal backs them up (as myapp.0.1.0.backup) before deleting them, and upgrades put changed ones aside rather than overwriting your edits.

Removing a Package and Its Dependents

Remove a package, cascading to the packages that depend on it (sinks first), with -c:

zick remove -k mylib -c

Preview the removal without touching anything:

zick remove -k mylib -c -r

The result lists every package that would be removed.

Finding Cruft

List the installed packages that nothing depends on — a good place to look when pruning a project:

zick orphans

Each reported package is a source node of the dependency graph: nothing installed depends on it.

Using zick in CI

A reproducible install step for a checkout in CI looks like this:

zick init
zick add -k mylib -V 1.2.0 -l https://example.com/mylib-1.2.0.zip
zick add -k myapp -V 0.1.0 -l https://example.com/myapp.zip -u mylib
zick verify -k myapp

Because every add records the files it installed and every verify checks them against the store, the step is repeatable and auditable: the same commands produce the same tree, and a partial or corrupt install fails the build with a precise report.

Installing What a Resolver Picked

When zick is paired with a dependency resolver, the resolver decides which versions a build needs and returns their URLs; zick installs exactly those archives:

# resolver picks versions and prints locations, e.g.:
# mylib 1.2.0 https://example.com/mylib-1.2.0.zip
# myapp 0.1.0 https://example.com/myapp.zip

zick init
zick add -k mylib -V 1.2.0 -l https://example.com/mylib-1.2.0.zip
zick add -k myapp -V 0.1.0 -l https://example.com/myapp.zip -u mylib
zick verify -k myapp

zick takes the versions it is given and has no opinion about version selection, so the two tools compose cleanly in a build.

For the full picture — the resolver outputting its install-ordered packages as JSON and a script piping them into zick add with jq — see "Using zick with the Resolver" in the longer example.
